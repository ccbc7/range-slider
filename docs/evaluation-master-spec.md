# 評価マスタ 設計メモ

このレンジスライダーで設定した「割合（%）」を **評価マスタ** とみなし、
数値データの並び順から各人にランク（評価）を付与する仕組みの設計案。

---

## 1. 概要

- スライダーで決めた区分と割合（例：`S = 5%` / `A = 95%`）を **マスタ** として DB に保存する。
- 一覧画面に「評価を受ける人」が並んでいる。
- 「評価実行」ボタンを押すと、各人の数値（スコア）をもとにマスタの割合で区切り、
  該当ランクの **評価文** が各人に適用される。
- 評価ロジックに渡る引数は **数値の配列だけ**（人物 ID 等は持たない＝配列の並び順で人物と対応づける）。

### 例

マスタ: `S = 5%`, `A = 95%`（S が上位）
入力: `[10, 100, 120, 55, 21]`

降順に並べると `120, 100, 55, 21, 10`。
上位 5% に入るのは先頭の `120` → **S**、残り 4 件 → **A**。

| 元の値 | 並び順位 | ランク |
| ---: | ---: | :--- |
| 120 | 1 | S |
| 100 | 2 | A |
| 55 | 3 | A |
| 21 | 4 | A |
| 10 | 5 | A |

---

## 2. マスタのデータ構造

ランクは **上位から下位の順**で並び、`percentage` の合計は必ず **100**。

```jsonc
{
  "id": "master_001",
  "name": "標準評価マスタ",
  "direction": "desc",      // desc=数値が高いほど上位 / asc=低いほど上位
  "ranks": [
    { "order": 1, "label": "S", "percentage": 5,  "evaluation_text": "卓越。期待を大きく上回る。" },
    { "order": 2, "label": "A", "percentage": 95, "evaluation_text": "良好。期待どおり。" }
  ]
}
```

制約:
- `percentage` 合計 = 100（保存時にバリデーション）。
- 各区分は最低 1%（スライダーの `MIN_RANGE_PERCENT` と一致）。
- `order` は連続・一意。`label` も一意。

---

## 3. 評価ロジック

### 考え方

1. 入力値を `direction` に従って並べ替える（`desc` なら降順 = 高い方が上位）。
2. マスタの割合を **上位からの累積割合** に変換する。
   - 例: `S 5% / A 95%` → 累積境界 `S = 0.05`, `A = 1.00`。
3. 各人の「上位から占める位置の下端」 `lower = pos / N`（`pos` は 0 始まりの順位、`N` は人数）を求め、
   `累積境界 > lower` となる **最初の区分** に割り当てる。

この「位置の下端で切る」方式により、
- 区分ごとの人数は割合に比例しつつ、
- 合計は常に `N` に一致し（取りこぼし・重複なし）、
- 例のように `N=5` でも上位 1 名が `S` になる（5% の帯に先頭が必ず入る）。

> **最上位区分は最低 1 名を保証**: 順位 1 位は `lower = 0` なので、最上位帯の割合が
> 1% でも必ず最上位区分へ入る（§6.1 の確定方針）。下位区分は空になり得る（許容）。

### 擬似コード

```ts
type Rank = { label: string; percentage: number; evaluation_text: string };

function evaluate(values: number[], master: { direction: "desc" | "asc"; ranks: Rank[] }) {
  const N = values.length;
  const ranks = master.ranks; // 上位順・percentage合計=100

  // 例外: 人数より区分数が多いと全区分を表現できない → 評価不能
  if (N < ranks.length) {
    throw new Error("評価不能: 人数より区分数が多い");
  }

  // 元のindexを保持したままソート
  const indexed = values.map((v, i) => ({ i, v }));
  indexed.sort((a, b) => (master.direction === "desc" ? b.v - a.v : a.v - b.v));

  // 累積境界（0〜1）
  const cum: number[] = [];
  let acc = 0;
  for (const r of ranks) {
    acc += r.percentage;
    cum.push(acc / 100);
  }

  // 割り当て
  const result: { value: number; rank: string; text: string }[] = new Array(N);
  indexed.forEach((item, pos) => {
    const lower = pos / N;
    const rankIdx = cum.findIndex((c) => c > lower);
    const rank = ranks[rankIdx];
    result[item.i] = { value: item.v, rank: rank.label, text: rank.evaluation_text };
  });

  return result; // 入力配列と同じ並びで返る
}
```

## 4. DB 設計（案）

```
evaluation_master
  id              PK
  name            マスタ名
  direction       'desc' | 'asc'
  version         整数（マスタ更新ごとに増やす）
  created_at
  updated_at

evaluation_master_rank
  id              PK
  master_id       FK -> evaluation_master.id
  sort_order      上位からの並び順（1,2,3...）
  label           'S' 'A' ...
  percentage      整数（合計100）
  evaluation_text 評価文
```

- マスタは更新され得るため `version` を持ち、**評価実行時の結果には使ったマスタの version を記録**しておく（後から設定が変わっても過去結果の根拠を追える）。

---

## 5. 画面・処理フロー

1. 一覧画面に評価対象者が並ぶ（各人は数値スコアを持つ）。
2. 「評価実行」ボタン押下。
3. スコアの配列をマスタへ渡す（並び順 = 一覧の並び順）。
4. ロジックが各人にランクと評価文を返す。
5. 一覧にランク・評価文を反映（必要なら結果を保存）。

> ⚠️ 配列の並び順が人物と 1:1 で対応する前提。一覧のソート変更や欠損があると対応がずれるため、
> 呼び出し側で「配列のindex ↔ 人物」の対応を固定すること。

## 6. 例外・エラー仕様

| ケース | 挙動 |
| :--- | :--- |
| 人数 `N` < 区分数 | **評価不能**（例: 2 人に S/A/B の 3 区分）。評価を実行せずエラー表示。 |
| `percentage` 合計 ≠ 100 | マスタ保存時にバリデーションエラー。 |
| `N = 0`（対象者なし） | 評価不能（または「対象なし」で正常終了）。要件で確定。 |
| 入力に数値以外 / `NaN` | 不正入力としてエラー（引数は数値のみの想定）。 |

### 6.1 「どこまでを評価不能とするか」の線引き

評価不能の判定は 1 種類ではなく、**原因のレベル**で分けて扱うのが安全。
レベルごとに「ブロックする／警告して続行する／そのまま許容する」を決めておく。

| レベル | 状況 | 例 | 推奨対応 |
| :--- | :--- | :--- | :--- |
| ① 構造的に不可能 | 人数 `N` < 区分数。各区分に最低 1 人を置くことすらできない | 2 人 / 3 区分 | **ハードエラー（実行不可）** |
| ② マスタ設定の矛盾 | `percentage` 合計 ≠ 100、区分0個 など。データ以前にマスタが不正 | 合計 98% | **保存時にブロック**（評価まで到達させない） |
| ③ 分布起因の空区分 | `N` ≥ 区分数だが、割合と分布の関係で **誰もいない区分**が出る | N=5 で `S5/A5/B90` → A が空 | **方針を選ぶ**（許容 / 警告 / エラー）。下記参照 |
| ④ スコアが無差別 | 全員同値で順位が付かない、または同値が境界をまたぐ | `[50,50,50,50]` | **方針を選ぶ**（全員同ランク / 警告 / エラー） |

#### ③ をどう扱うか（要合意）

- **許容**: 空区分があってもよい（割合は「枠の上限」と解釈）。一覧運用ではこれが自然なことが多い。
- **警告**: 実行はするが「A 区分に該当者なし」を画面に出す。
- **エラー**: 全区分に最低 1 人いることを要件にするなら不能扱い。

> 目安: **①②は常にブロック**、**③④は運用要件しだい**。
> まずは「①②＝評価不能、③④＝許容（必要なら警告）」を初期方針にし、
> 厳密運用が要るマスタだけ③④もエラーに切り替えられるようにしておくと拡張しやすい。

#### 確定方針: 最上位区分は最低 1 名を保証

- **少人数でも、最上位区分には必ず最低 1 名が割り当てられる**ことを自然な挙動とする。
- 本書の位置ベース方式（順位 1 位は `lower = 0` で必ず最上位帯に入る）により、
  最上位帯の割合が 1% でもこの保証は構造的に満たされる（特別な分岐は不要）。
- 一方、**中位・下位の区分は空になり得る**（③）。これは許容とし、
  「割合 = その区分に入り得る上限の枠」と解釈する。
- 例: `S5% / A95%` に 5 名 → 必ず S に 1 名（先頭）、残りは A。
  `S5% / A5% / B90%` に 5 名 → S に 1 名は保証、A は空になり得るが許容。

## 7. 懸念事項・要確認

1. **同値（タイ）の扱い**
   `[100, 100, 90, ...]` のように同じスコアが境界をまたぐと、同点なのに別ランクになり得る。
   → 「同スコアは同ランクに揃える」ルールが必要か要検討（揃える場合は上位側/下位側どちらに寄せるか）。

2. **小サンプルでの丸め感覚**
   `N` が小さいと「5%」がきれいに 1 人に対応しない。今回の方式は位置の下端で切るため
   先頭が必ず最上位帯に入るが、「割合どおりの人数」とは一致しない点は周知が必要。

3. **数値の方向（高い/低いが良い）**
   指標によっては低い方が良い（例: ミス件数）。`direction` で吸収する設計にしているが、
   マスタごとに固定でよいか、指標単位で切り替えるか要確認。

4. **マスタ変更と過去結果の整合**
   評価後にマスタを変えると基準が変わる。`version` を結果に記録する想定だが、
   再評価の運用（自動/手動、履歴の保持期間）を決める必要あり。

5. **配列と人物の対応**
   引数が数値のみのため、並び順ズレ＝評価ズレに直結する。呼び出し側の責務範囲を明確にする。

6. **区分の最小割合**
   1% 区分を多数作ると小サンプルでは実質割り当て不能な帯が出る。
   区分数の上限や「最小割合 × 区分数 ≦ 100」以上のチェックがあると安全。

7. **境界の解釈の合意**
   「上位 5%」を *人数ベース*（round/floor/ceil）で数えるか、本書のような *位置ベース* で切るかは
   結果が変わる。関係者と定義を合意しておくこと（本書は位置ベースで先頭が最上位帯に入る方式）。
